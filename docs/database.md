## 1. ภาพรวมและความสัมพันธ์ของตาราง

```
auth.users (ระบบล็อกอินของ Supabase)
   │  ├── students.auth_user_id   (นิสิตผูกบัญชีล็อกอินด้วยอีเมล)
   │  └── staff.user_id           (เจ้าหน้าที่ = ป้อมยาม หรือ ผู้ดูแลระบบ)
   │
students (D1) 1 ───< loans (D3) >─── 1 bikes (D2) 1 ─── 1 bike_locks (D2: รหัสล็อก)
                        │
                        └─ received_by → staff.user_id (ป้อมยามที่รับคืน)
```

หลักการออกแบบ 3 ข้อ:
1. **ตาราง `loans` ห้ามเขียนตรงจากแอป** ทุกการยืม/คืนต้องผ่านฟังก์ชัน `borrow_bike` / `return_bike` เพื่อให้กฎ (ยืมได้ครั้งละ 1 คัน ต้องเป็นหอใน ฯลฯ) ถูกบังคับที่ฐานข้อมูลเสมอ ไม่ขึ้นกับว่าแอปเขียนถูกหรือไม่
2. **รหัสล็อกล้ออยู่คนละตารางกับข้อมูลจักรยาน** นิสิตอ่านตรงๆ ไม่ได้ จะได้รหัสเฉพาะคันที่ตัวเองยืมอยู่เท่านั้น
3. **แต่ละคนเห็นเฉพาะข้อมูลที่ควรเห็น** (Row Level Security) นิสิตเห็นแค่ของตัวเอง ป้อมยามเห็นทั้งหมด

## 2. ตารางทั้งหมด

### `students` — D1 ข้อมูลนิสิตหอใน
ผู้ดูแลระบบนำเข้ารายชื่อทุกเทอม นิสิตล็อกอินครั้งแรกแล้วระบบผูกบัญชีให้เองด้วยอีเมล (ฟังก์ชัน `claim_student_profile`)

| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `student_id` | text, **PK** | รหัสนิสิต เช่น `66000001` |
| `full_name` | text, ไม่ว่าง | ชื่อ-นามสกุล |
| `building`, `room` | text | อาคาร, ห้อง |
| `phone`, `email` | text | เบอร์โทร, อีเมลมหาลัย (**อีเมลห้ามซ้ำ** ไม่สนตัวพิมพ์เล็ก-ใหญ่) |
| `semester` | text, ไม่ว่าง | ภาคเรียนที่มีสิทธิ์ เช่น `1/2569` |
| `verified` | boolean, default `false` | ยืนยันหอในแล้วหรือยัง (ตั้งเป็น true ตอนผูกบัญชี) นิสิตที่ `false` ยืมไม่ได้ |
| `late_count` | integer, default 0 | จำนวนครั้งที่คืนสาย (เพิ่มอัตโนมัติใน `return_bike` อย่าแก้เอง) |
| `auth_user_id` | uuid, unique | บัญชีล็อกอินที่ผูกกับนิสิตคนนี้ (ว่างจนกว่าจะล็อกอินครั้งแรก) |
| `created_at` | timestamptz | เวลาที่เพิ่มแถว |

### `staff` — เจ้าหน้าที่ (ไม่อยู่ในแผนเดิม)
| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `user_id` | uuid, **PK** → `auth.users` | บัญชีล็อกอินของเจ้าหน้าที่ |
| `full_name` | text | ชื่อ |
| `role` | text | `guard` (ป้อมยาม) หรือ `admin` (ผู้ดูแลระบบ) |

ใครอยู่ในตารางนี้ = เป็นเจ้าหน้าที่ **เพิ่มเจ้าหน้าที่ใหม่ผ่าน SQL Editor เท่านั้น** (ไม่มีหน้าในแอป):
```sql
insert into public.staff (user_id, full_name, role)
select id, 'ชื่อเจ้าหน้าที่', 'guard'      -- หรือ 'admin'
from auth.users where email = 'อีเมลที่สร้างใน Authentication > Users แล้ว';
```

### `bikes` — D2 ข้อมูลจักรยาน
| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `bike_no` | text, **PK** | หมายเลขจักรยาน เช่น `B01` |
| `qr_code` | text, unique | ค่าที่อยู่ใน QR บนตัวจักรยาน **เก็บแค่เลขคัน** (ตอนนี้ค่าเท่ากับ `bike_no`) |
| `station` | text | จุดจอด |
| `status` | text | `available` / `borrowed` / `broken` (ดูหัวข้อ 7) เปลี่ยนโดยฟังก์ชันตอนยืม/คืน หรือโดยแอดมิน |
| `note` | text | หมายเหตุความเสียหาย (ใส่ตอนรับคืนแบบชำรุด) |

### `bike_locks` — D2 รหัสล็อกล้อ (แยกตาราง)
| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `bike_no` | text, **PK** → `bikes` | คันไหน |
| `lock_code` | text | รหัสล็อกล้อ **ห้ามแสดงให้ใครนอกจากผู้ยืมคันนั้นและเจ้าหน้าที่** |

แยกตารางเพราะถ้าอยู่ใน `bikes` นิสิตทุกคนจะ `select` เห็นรหัสทุกคัน และรหัสจะถูกส่งออกทาง Realtime ด้วย

### `loans` — D3 ข้อมูลการยืม-คืน
| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `loan_id` | bigint, **PK** (รันเลขเอง) | เลขรายการ |
| `student_id` | text → `students` | ผู้ยืม |
| `bike_no` | text → `bikes` | คันที่ยืม |
| `borrowed_at` | timestamptz | เวลายืม |
| `due_at` | timestamptz | กำหนดคืน = **21.00 น. เวลาไทย** ของวันที่ยืม |
| `returned_at` | timestamptz | เวลาคืนจริง (ว่าง = ยังไม่คืน) |
| `received_by` | uuid → `staff` | ป้อมยามที่รับคืน |
| `condition` | text | ผลตรวจตอนรับคืน `normal` / `damaged` |
| `status` | text | `borrowing` / `overdue` / `returned` (ดูหัวข้อ 7) |
| `is_late` | boolean | คืนสายหรือไม่ (ตัดสินตอนรับคืน: คืนหลัง `due_at`) |

ข้อจำกัดที่ฐานข้อมูลบังคับ: `status = 'returned'` ก็ต่อเมื่อมี `returned_at` · มี **รายการค้างได้ไม่เกิน 1 รายการต่อนิสิต และต่อจักรยาน** (unique index) กันกดยืมซ้ำพร้อมกัน

## 3. ใครอ่าน/เขียนอะไรได้ (สิทธิ์)

| ตาราง | นิสิต | ป้อมยาม (`guard`) | ผู้ดูแล (`admin`) | ยังไม่ล็อกอิน |
|---|---|---|---|---|
| `students` | อ่านแถวตัวเองเท่านั้น | อ่านทั้งหมด | อ่าน + เพิ่ม/แก้/ลบ ทั้งหมด | ไม่ได้ |
| `staff` | ไม่เห็น | เห็นแถวตัวเอง | เห็นทั้งหมด (แก้ผ่าน SQL Editor) | ไม่ได้ |
| `bikes` | อ่านทั้งหมด | อ่านทั้งหมด | อ่าน + เพิ่ม/แก้/ลบ | ไม่ได้ |
| `bike_locks` | **ไม่เห็นเลย** (ได้ 0 แถว) | อ่านทั้งหมด | อ่าน + เพิ่ม/แก้/ลบ | ไม่ได้ |
| `loans` | อ่านรายการของตัวเอง | อ่านทั้งหมด | อ่านทั้งหมด | ไม่ได้ |

- **`loans` ไม่มีใครเขียนตรงได้ แม้แต่แอดมิน** ต้องผ่านฟังก์ชัน
- ถ้าแอปได้ข้อมูลว่าง (0 แถว) ทั้งที่ในตารางมีข้อมูล มักเป็นเพราะสิทธิ์ ไม่ใช่บั๊ก: เช็กก่อนว่าล็อกอินด้วยบัญชีบทบาทอะไร
- ป้อมยามแก้ `bikes` ตรงๆ ไม่ได้ สถานะจักรยานเปลี่ยนผ่าน `return_bike` เท่านั้น ส่วนการ "ปิดงานซ่อม" (broken → available) เป็นงานของแอดมิน

## 4. ฟังก์ชัน (เรียกด้วย rpc)

เรียกจากแอปด้วย `supabase.rpc('ชื่อฟังก์ชัน', params: {...})` ทุกฟังก์ชันต้องล็อกอินก่อน ผลลัพธ์เป็น JSON (Map) ชื่อฟิลด์เป็น snake_case ตามตาราง
ทุกฟังก์ชันที่ผิดกติกาจะ **โยน error ที่มีข้อความเป็นรหัสสั้นๆ** เช่น `already_borrowing` ให้จับที่ `PostgrestException.message` (ตารางรหัสอยู่หัวข้อ 5)

### 4.1 `claim_student_profile()` — process 1.0
ผูกบัญชีที่ล็อกอินอยู่กับรายชื่อหอใน โดยจับคู่ **อีเมลของบัญชี** กับ `students.email` แล้วตั้ง `verified = true` และ `auth_user_id`
- เรียกเมื่อ: ล็อกอินสำเร็จ และไม่ใช่เจ้าหน้าที่ (ไม่มีแถวใน `staff`)
- คืน: แถว `students` ของคนนั้น (ถ้าเคยผูกแล้ว คืนแถวเดิม ไม่ error → เรียกซ้ำได้ทุกครั้งที่เปิดแอป)
- error: `not_authenticated`, `not_in_dorm_list` (อีเมลนี้ไม่อยู่ในรายชื่อ หรือรายชื่อนั้นถูกผูกกับบัญชีอื่นไปแล้ว)
```dart
final row = await supabase.rpc('claim_student_profile');   // Map<String, dynamic>
```

### 4.2 `borrow_bike(p_qr_code text)` — process 3.0
ยืมจักรยาน ตรวจครบทุกกฎใน transaction เดียว แล้วคืนรหัสล็อก
- เรียกเมื่อ: นิสิตสแกน QR (ค่าที่สแกนได้ส่งเป็น `p_qr_code`) แล้วกดยืนยัน
- ตรวจตามลำดับ: นิสิตผูกบัญชีและ `verified` → ไม่มีรายการยืมค้าง → มีจักรยานคันนี้ → สถานะ `available` → มีรหัสล็อก → ยังไม่เลย 21.00 น.
- ผลข้างเคียง: เพิ่มแถวใน `loans` (`status = borrowing`, `due_at` = 21.00 น. วันนี้) และตั้ง `bikes.status = borrowed`
- คืน:
```json
{ "loan_id": 12, "bike_no": "B01", "lock_code": "0111",
  "borrowed_at": "2026-10-10T04:30:00+00:00", "due_at": "2026-10-10T14:00:00+00:00" }
```
- error: `not_verified`, `already_borrowing`, `bike_not_found`, `bike_not_available`, `no_lock_code`, `after_hours`
```dart
final res = await supabase.rpc('borrow_bike', params: {'p_qr_code': scannedValue});
final loan = res as Map<String, dynamic>;
```
> เวลาในผลลัพธ์เป็น ISO 8601 (UTC) ใช้ `DateTime.parse(s).toLocal()` แปลงเป็นเวลาในเครื่องก่อนแสดง

### 4.3 `get_my_active_loan()` — process 3.0 / 4.0
ดูรายการที่ตัวเองยืมค้างอยู่ พร้อมรหัสล็อก
- เรียกเมื่อ: เปิดแอป / กลับมาหน้าหลักของนิสิต (ถ้าแอปปิดไปแล้วเปิดใหม่ ต้องยังเห็นรหัสล็อกและเวลานับถอยหลัง)
- คืน: JSON แบบเดียวกับ `borrow_bike` เพิ่ม `status` หรือ **`null`** ถ้าไม่มีรายการค้าง
- `status` เป็น `overdue` ทันทีที่เลย `due_at` แม้ฐานข้อมูลยังเป็น `borrowing` อยู่ (คำนวณให้ตอนอ่าน)
```dart
final res = await supabase.rpc('get_my_active_loan');   // null ถ้าไม่ได้ยืมอยู่
```
> **อย่าเก็บรหัสล็อกไว้ในเครื่อง/ไฟล์/log** ดึงใหม่จากฟังก์ชันนี้ทุกครั้งที่จะแสดง

### 4.4 `return_bike(p_bike_no text, p_condition text, p_note text = null)` — process 5.0
รับคืน + บันทึกผลตรวจสภาพ (เฉพาะเจ้าหน้าที่)
- `p_condition` = `normal` หรือ `damaged` · ถ้า `damaged` **ต้องใส่ `p_note`**
- ผลข้างเคียง: ปิดรายการยืม (`returned_at`, `received_by`, `condition`, `is_late`, `status = returned`) · ตั้ง `bikes.status` เป็น `available` (ปกติ) หรือ `broken` + บันทึก `note` (ชำรุด) · ถ้าคืนสาย `students.late_count` +1
- คืน:
```json
{ "loan_id": 12, "student_id": "66000001", "bike_no": "B01",
  "returned_at": "...", "is_late": false, "condition": "normal" }
```
- error: `staff_only`, `invalid_condition`, `note_required`, `no_active_loan`
```dart
await supabase.rpc('return_bike', params: {
  'p_bike_no': 'B01', 'p_condition': 'damaged', 'p_note': 'เบรกหลังเสีย',
});
```
> ก่อนเรียก ป้อมยามต้อง **เห็นข้อมูลผู้ยืม** ก่อน (ดูหัวข้อ 4.7) แล้วค่อยกดยืนยัน

### 4.5 `mark_overdue_loans()` — process 4.0
ตั้ง `status = overdue` ให้ทุกรายการที่ยังไม่คืนและเลย `due_at` แล้ว คืนจำนวนที่อัปเดต (integer) เรียกซ้ำกี่ครั้งก็ได้ไม่เสียหาย
- ใครเรียกก็ได้ที่ล็อกอินแล้ว ตัวอย่างที่เหมาะ: ป้อมยามเปิดหน้ารายการเกินเวลา
- อยากให้ฐานข้อมูลทำเองทุก 5 นาที: เปิด extension `pg_cron` แล้วเอาคำสั่งที่ comment ไว้ท้ายหัวข้อ 6 ของ `001_init.sql` ไปรัน (ไม่บังคับ)
```dart
final changed = await supabase.rpc('mark_overdue_loans');   // int
```

### 4.6 `is_staff()` / `is_admin()`
ใช้ภายในกฎสิทธิ์ เรียกจากแอปได้ถ้าอยากรู้ว่าตัวเองเป็นเจ้าหน้าที่ไหม (คืน true/false) แต่ **วิธีแนะนำสำหรับหาบทบาทคือ `select` แถวตัวเองจากตาราง `staff`** เพราะได้ `role` มาเลย
```dart
final me = await supabase.from('staff').select('role, full_name')
    .eq('user_id', supabase.auth.currentUser!.id).maybeSingle();   // null = ไม่ใช่เจ้าหน้าที่
```

### 4.7 คำสั่งอ่านข้อมูลที่ใช้บ่อย (ผ่านตารางโดยตรง)
```dart
// 2.0 รายการจักรยานทั้งหมด (นิสิต/ป้อมยามอ่านได้) ไม่มีรหัสล็อก
final bikes = await supabase.from('bikes')
    .select('bike_no, qr_code, station, status, note').order('bike_no');

// 6.0 รายการที่ยังค้างอยู่ พร้อมข้อมูลผู้ยืม (เฉพาะเจ้าหน้าที่ เพราะนิสิตเห็นแค่ของตัวเอง)
final active = await supabase.from('loans')
    .select('*, students(full_name, building, room, phone)')
    .isFilter('returned_at', null);

// 6.0 ค้นประวัติด้วยรหัสนิสิต
final history = await supabase.from('loans').select()
    .eq('student_id', '66000001').order('borrowed_at', ascending: false);

// 7.0 แอดมินนำเข้ารายชื่อ: ส่งเฉพาะคอลัมน์เหล่านี้ (อย่าส่ง verified / late_count / auth_user_id
// ไม่งั้นจะทับสถานะของคนที่ผูกบัญชีแล้ว)
await supabase.from('students').upsert(rows, onConflict: 'student_id');

// 7.0 แอดมินปิดงานซ่อม
await supabase.from('bikes').update({'status': 'available', 'note': null}).eq('bike_no', 'B01');
```
> ตัวอย่างในหัวข้อนี้เขียนตามเอกสาร supabase_flutter แต่ **ยังไม่ได้ลองรันกับ Supabase จริง** ถ้ารันแล้วพังให้แก้ตัวอย่างในเอกสารนี้ด้วย

## 5. รหัสข้อผิดพลาด

ฟังก์ชันโยน `PostgrestException` ที่ `message` เป็นรหัสด้านล่าง คนที่ 1 ทำฟังก์ชันแปลงรหัสเป็นข้อความไทยไว้ที่ `lib/core/errors/app_error.dart` ให้ทุกคนใช้ร่วมกัน

| รหัส | โยนจาก | เกิดเมื่อ | ข้อความที่ควรแสดงให้ผู้ใช้ |
|---|---|---|---|
| `not_authenticated` | `claim_student_profile` | ยังไม่ได้ล็อกอิน | กรุณาเข้าสู่ระบบก่อน |
| `not_in_dorm_list` | `claim_student_profile` | อีเมลไม่อยู่ในรายชื่อหอใน | ไม่พบอีเมลนี้ในรายชื่อนิสิตหอใน กรุณาติดต่อกองหอพัก |
| `not_verified` | `borrow_bike` | ยังไม่ได้ผูกบัญชี หรือ `verified = false` | บัญชีนี้ยังไม่ได้ยืนยันสิทธิ์หอใน |
| `already_borrowing` | `borrow_bike` | มีจักรยานที่ยืมค้างอยู่ | คุณมีจักรยานที่ยืมค้างอยู่ ต้องคืนก่อน |
| `bike_not_found` | `borrow_bike` | QR ไม่ตรงกับคันไหนเลย | ไม่พบจักรยานคันนี้ ลองสแกนอีกครั้ง |
| `bike_not_available` | `borrow_bike` | คันนี้ถูกยืมอยู่หรือชำรุด | จักรยานคันนี้ไม่ว่าง |
| `no_lock_code` | `borrow_bike` | คันนี้ยังไม่มีแถวใน `bike_locks` | จักรยานคันนี้ยังไม่มีรหัสล็อก แจ้งผู้ดูแล |
| `after_hours` | `borrow_bike` | ยืมหลัง 21.00 น. | เลยเวลา 21.00 น. แล้ว ยืมไม่ได้ |
| `staff_only` | `return_bike` | ผู้เรียกไม่ใช่เจ้าหน้าที่ | ฟังก์ชันนี้สำหรับเจ้าหน้าที่เท่านั้น |
| `invalid_condition` | `return_bike` | `p_condition` ไม่ใช่ `normal`/`damaged` | (บั๊กในแอป ไม่ควรเกิด) |
| `note_required` | `return_bike` | ชำรุดแต่ไม่ใส่หมายเหตุ | ถ้าชำรุด ต้องใส่หมายเหตุ |
| `no_active_loan` | `return_bike` | คันนี้ไม่มีใครยืมอยู่ | ไม่พบรายการยืมค้างของคันนี้ |

error อื่นๆ (เช่น `permission denied`, `violates ...`) แปลว่าแอปทำอะไรที่ไม่ได้รับอนุญาต หรือชนข้อจำกัดของฐานข้อมูล ไม่ใช่ความผิดของผู้ใช้ ให้ log ไว้ดูเอง

## 6. กติกาธุรกิจที่ฐานข้อมูลบังคับให้

แอปไม่ต้อง (และไม่ควร) ตรวจซ้ำเอง แค่แสดงข้อความตามรหัส error แต่แอปควรซ่อนปุ่มที่ไม่มีทางสำเร็จเพื่อ UX ที่ดี

1. ยืมได้ต่อเมื่อผูกบัญชีแล้วและ `verified = true`
2. นิสิต 1 คนยืมได้ครั้งละ **1 คัน** · จักรยาน 1 คันถูกยืมได้ครั้งละ **1 คน** (ล็อกที่ระดับฐานข้อมูล กันกดพร้อมกัน)
3. กำหนดคืนคือ **21.00 น. เวลาไทยของวันที่ยืม** ยืมหลัง 21.00 น. ไม่ได้
4. จักรยานที่ `broken` หรือ `borrowed` ยืมไม่ได้
5. การคืนทำได้โดยเจ้าหน้าที่เท่านั้น ถ้าชำรุดต้องมีหมายเหตุ และจักรยานจะเป็น `broken` จนกว่าแอดมินปิดงานซ่อม
6. คืนหลัง `due_at` = `is_late = true` และ `late_count` ของนิสิต +1 (ยังไม่มีการระงับสิทธิ์ เพราะยังไม่ตกลงกติกา ดูหัวข้อ 14)

## 10. สูตร SQL ช่วยทดสอบ

รันใน SQL Editor ซึ่งทำงานเป็นเจ้าของฐานข้อมูล ข้ามกฎสิทธิ์ทั้งหมด **ใช้กับข้อมูลทดสอบเท่านั้น**

```sql
-- สร้างรายการยืมปลอมให้ B03 (เพื่อให้คนที่ 3 ทดสอบรับคืนได้โดยไม่ต้องรอแอปยืมเสร็จ)
insert into public.loans (student_id, bike_no, due_at)
values ('66000003', 'B03', now() + interval '2 hours');
update public.bikes set status = 'borrowed' where bike_no = 'B03';

-- ทำให้รายการนั้น "เกินเวลา" (ทดสอบหน้าเกินเวลา / คืนสาย)
update public.loans set due_at = now() - interval '30 minutes'
where bike_no = 'B03' and returned_at is null;

-- ดูรายการที่ยังค้างอยู่ พร้อมชื่อผู้ยืม
select l.loan_id, l.bike_no, s.full_name, l.due_at, l.status
from public.loans l join public.students s using (student_id)
where l.returned_at is null;

-- รีเซ็ตการยืมทั้งหมดกลับเป็นเริ่มต้น (ลบประวัติ! ใช้เฉพาะช่วงพัฒนา)
delete from public.loans;
update public.bikes set status = 'available', note = null;
update public.students set late_count = 0;

-- เปลี่ยนเทอม: นำเข้ารายชื่อใหม่ (semester ใหม่) ก่อน แล้วปิดสิทธิ์คนเทอมเก่า
update public.students set verified = false where semester <> '1/2570';   -- ใส่เทอมปัจจุบัน
-- อย่าลบแถวนิสิตเก่า ถ้ามีประวัติการยืมจะลบไม่ได้ (foreign key) และเราอยากเก็บประวัติไว้
```

## 11. Realtime

ตาราง `bikes` และ `loans` อยู่ใน publication `supabase_realtime` แล้ว จึงฟังการเปลี่ยนแปลงสดได้ (ใช้กับหน้า 2.0 จักรยานว่าง และหน้าสถานะของป้อมยาม)
```dart
supabase.from('bikes').stream(primaryKey: ['bike_no']).listen((rows) { ... });
```
- `bike_locks` **ไม่อยู่ใน** Realtime โดยตั้งใจ เพราะมีรหัสล็อก

- ถ้า stream ไม่เด้ง ให้เช็กใน Dashboard → Database → Publications → `supabase_realtime` ว่ามี `bikes` กับ `loans`

## 12. ความปลอดภัย: ต้องรู้

- `anon key` อยู่ในแอปได้ (ออกแบบมาให้เปิดเผยได้ เพราะความปลอดภัยอยู่ที่กฎสิทธิ์ในฐานข้อมูล) แต่ **อย่า commit `env.json`** เพื่อไม่ให้คนอื่นนำไปยิงโปรเจกต์ของทีม
- **`service_role` key ข้ามกฎสิทธิ์ทั้งหมด ห้ามอยู่ในแอป ในโค้ด หรือใน repo**
- การผูกบัญชีนิสิตใช้ **อีเมลของบัญชีล็อกอิน** จับคู่กับ `students.email` ดังนั้น **ต้องแน่ใจว่าเจ้าของอีเมลเป็นคนนั้นจริง**:
  - ถ้าใช้อีเมล+รหัสผ่านและปิด "Confirm email" ใน Supabase ใครก็สมัครด้วยอีเมลของคนอื่นแล้วผูกสิทธิ์แทนได้
  - ช่วงพัฒนา เราสร้างบัญชีเองจาก Dashboard จึงปลอดภัย แต่ก่อนใช้จริงต้องเลือกทางใดทางหนึ่ง: เปิด Confirm email, หรือใช้ล็อกอินผ่านผู้ให้บริการของมหาวิทยาลัย (เช่น Google/Microsoft ที่ยืนยันอีเมลให้แล้ว)
- ข้อมูลใน `seed.sql` เป็นของปลอม ห้ามใส่ข้อมูลจริงของนิสิต (ชื่อ/เบอร์/รหัส) ใน repo

## 13. ที่ต่างจากแผน

Data Dictionary ในแผน (`docs/bike-system-plan.html`) ยังใช้ได้ โดยมี 3 จุดที่ต่างเพื่อให้ปลอดภัยและใช้งานได้จริง:

| จุด | ในแผน | ในฐานข้อมูลจริง | เหตุผล |
|---|---|---|---|
| รหัสล็อก | `lock_code` อยู่ใน D2 (`bikes`) | แยกเป็นตาราง `bike_locks` (ยังนับเป็น D2 ส่วนหนึ่ง) | ไม่ให้นิสิตอ่านรหัสทุกคันได้ และไม่รั่วทาง Realtime |
| บัญชีล็อกอิน | D1 ไม่มีฟิลด์เชื่อมบัญชี | เพิ่ม `students.auth_user_id` | ต้องรู้ว่าบัญชีล็อกอินไหนเป็นนิสิตคนไหน |
| เจ้าหน้าที่ | ไม่มีใน Data Dictionary | เพิ่มตาราง `staff` | ต้องรู้ว่าใครเป็นป้อมยาม/แอดมิน และเก็บ `received_by` |

นอกนั้นชื่อและความหมายของฟิลด์ใน D1–D3 ตรงกับแผนทุกตัว ค่าสถานะใช้ภาษาอังกฤษในฐานข้อมูล (หัวข้อ 7)

## 14. สถานะการทดสอบ และเรื่องที่ยังไม่ได้ตัดสินใจ

**ที่ทดสอบไปแล้ว:** รัน `001_init.sql` + `seed.sql` กับ Postgres จำลองในเครื่อง (PGlite) โดยจำลอง schema `auth` ของ Supabase ทดสอบ 52 ข้อผ่านทั้งหมด ครอบคลุม: รันซ้ำได้, คนนอกเข้าไม่ได้, นิสิตเห็นแค่ของตัวเอง, รหัสล็อกไม่รั่ว, ยืม/ยืมซ้อน/คันไม่ว่าง/QR มั่ว, ป้อมยามรับคืน (ปกติ/ชำรุด/คืนสาย), แอดมินจัดการข้อมูล, กันยืมซ้อนด้วย unique index

**ที่ยังไม่ได้ทดสอบ:** การรันบน Supabase จริง และการเรียกจากแอป Flutter รอบแรกที่คนที่ 1 รันไฟล์ใน Supabase ให้ดู error ในหน้า SQL Editor ถ้ามี แล้วแจ้งทีม

**เรื่องที่ทีมต้องตัดสินใจ (คำถามค้างจากแผน):**
